# BUG-007: POST /pet with a value of the wrong JSON type returns 500 instead of 405

- Id: BUG-007
- Status: Open
- Title: POST /pet with a value of the wrong JSON type returns 500 instead of 405
- Raised: 2026-11-17
- Endpoint: POST /pet
- Environment: https://petstore.swagger.io/v2
- Linked test: `A pet with a value of the wrong JSON type is rejected with 405 Invalid input and not stored` (`@bug:BUG-007`, PetStore_Pet_Validation.feature)

## Description

The `Pet` schema in `swagger.json` defines the JSON type of every field: `id` is an int64, `photoUrls` and
`tags` are arrays, `category` is an object, and the body itself is one `Pet` object. When a value has a type
the server cannot convert, `POST /pet` crashes with `500` instead of rejecting the request as invalid input.

## Steps to reproduce

1. `POST /pet` with body `{"id": 918274001, "name": "Rex", "photoUrls": "https://example.com/pet.jpg"}` (`photoUrls` is a string)
2. `POST /pet` with body `{"id": 918274002, "name": "Rex", "photoUrls": ["https://example.com/pet.jpg"], "category": "dogs"}` (`category` is a string)
3. `POST /pet` with body `{"id": 918274003, "name": "Rex", "photoUrls": ["https://example.com/pet.jpg"], "tags": "cute"}` (`tags` is a string)
4. `POST /pet` with body `{"id": "abc", "name": "Rex", "photoUrls": ["https://example.com/pet.jpg"]}` (`id` is not a number)
5. `POST /pet` with body `[{"name": "Rex", "photoUrls": ["https://example.com/pet.jpg"]}]` (an array instead of one pet)
6. `GET /pet/918274001`, `GET /pet/918274002` and `GET /pet/918274003`

## Expected

- Steps 1-5 are rejected with `405 Invalid input`.
- Step 6 returns `404` for all three: nothing is stored.

Basis: steps 1-5, the contract (the `Pet` schema types and the `405` response of `POST /pet`). The spec gives
`405` no schema, so no response body or message is expected. Step 6, an assumption: a rejected pet is not
added (the spec doesn't say so).

## Actual

- Steps 1-5 return `500` with `{"code":500,"type":"unknown","message":"something bad happened"}` (2026-11-17).
- Step 6 returns `404`: nothing is stored.

## Notes

Values the server can convert are accepted and converted, not rejected: `"name": 123` is stored as `"123"`,
`"photoUrls": [1]` as `["1"]`, `"id": "918274004"` as the number and `"id": 1.5` as `1`. They are not part of
this bug.

## Impact

Clients get a server error for a client-side mistake and cannot tell it from a real outage; monitoring counts
it as one.
