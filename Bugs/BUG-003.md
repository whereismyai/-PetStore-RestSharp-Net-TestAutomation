# BUG-003: POST /pet accepts and stores invalid pets

- Id: BUG-003
- Status: Open
- Title: POST /pet accepts and stores invalid pets
- Raised: 2026-11-14
- Updated: 2026-11-17 (missing name and photoUrls together, status in the wrong case, empty status added)
- Endpoint: POST /pet
- Environment: https://petstore.swagger.io/v2
- Linked tests: `A pet without a required field is rejected with 405 Invalid input and not stored` and `A pet with an invalid status is rejected with 405 Invalid input and not stored` (`@bug:BUG-003`, PetStore_Pet_Validation.feature)

## Description

The spec (`swagger.json`) marks `name` and `photoUrls` as required and `status` as an enum (`available`, `pending`, `sold`),
and defines `405 Invalid input` for `POST /pet`. The API does not validate any of these rules: it answers `200`
and stores the invalid pet.

## Steps to reproduce

1. `POST /pet` with body `{"id": 918273001, "status": "available", "photoUrls": ["https://example.com/pet.jpg"]}` (no `name`)
2. `POST /pet` with body `{"id": 918273002, "name": "Rex", "status": "flying", "photoUrls": ["https://example.com/pet.jpg"]}`
3. `POST /pet` with body `{"id": 918273003, "name": "Rex", "status": "available"}` (no `photoUrls`)
4. `POST /pet` with body `{"id": 918273004, "status": "available"}` (no `name`, no `photoUrls`)
5. `POST /pet` with body `{"id": 918273005, "name": "Rex", "status": "Available", "photoUrls": ["https://example.com/pet.jpg"]}` (enum value in the wrong case)
6. `POST /pet` with body `{"id": 918273006, "name": "Rex", "status": "", "photoUrls": ["https://example.com/pet.jpg"]}` (empty status)
7. `GET /pet/{id}` for each Id from steps 1-6

## Expected

- Steps 1-6 are rejected with `405 Invalid input`, as the spec defines.
- Step 7 returns `404` for all six: nothing invalid is stored.

Basis: steps 1-6, the contract (`required`, `enum` and the `405` response of `POST /pet`). The spec gives `405`
no schema, so no response body or message is expected. Step 7, an assumption: a rejected pet is not added
(the spec doesn't say so).

## Actual

- Step 1 returns `200` with `{"id":918273001,"photoUrls":["https://example.com/pet.jpg"],"tags":[],"status":"available"}`.
- Step 2 returns `200` with `{"id":918273002,"name":"Rex","photoUrls":["https://example.com/pet.jpg"],"tags":[],"status":"flying"}`.
- Step 3 returns `200` with `{"id":918273003,"name":"Rex","photoUrls":[],"tags":[],"status":"available"}`.
- Steps 4-6 return `200` too: `{"id":918273004,"photoUrls":[],"tags":[],"status":"available"}`, `"status":"Available"`
  and `"status":""` are stored as sent (2026-11-17).
- All six pets are stored (rechecked 2026-11-17).

## Notes

The linked scenario checks step 7 only after a `405`. A `GET` by the sent Id after an accepted or failed
`POST` proves nothing: the pet could be stored under another Id.

The server already answers malformed JSON with `400 bad input`, so `400` may be the better code; the test
follows the published spec (`405`) until the spec is changed.

## Impact

Data that breaks the contract gets into the store and reaches every client that reads it.
