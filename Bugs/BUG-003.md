# BUG-003: POST /pet accepts and stores invalid pets

- Id: BUG-003
- Status: Open
- Title: POST /pet accepts and stores invalid pets
- Raised: 2026-11-14
- Updated: 2026-11-17 (missing name and photoUrls together, null and empty name and photoUrls, status in the wrong case, empty status added; a number for a string, a decimal Id and null tags added)
- Endpoint: POST /pet
- Environment: https://petstore.swagger.io/v2
- Linked tests: `A pet with a missing, null or empty required field is rejected with 405 Invalid input and not stored`, `A pet with an invalid status is rejected with 405 Invalid input and not stored` and `A pet with a number for a string, a decimal Id or null tags is rejected with 405 Invalid input and not stored` (`@bug:BUG-003`, PetStore_Pet_Validation.feature)

## Description

The spec (`swagger.json`) marks `name` and `photoUrls` as required and `status` as an enum (`available`, `pending`, `sold`),
gives every field a type, and defines `405 Invalid input` for `POST /pet`. The API does not validate any of these
rules: it answers `200` and stores the invalid pet, converting or dropping values of the wrong type.

## Steps to reproduce

1. `POST /pet` with body `{"id": 918273001, "status": "available", "photoUrls": ["https://example.com/pet.jpg"]}` (no `name`)
2. `POST /pet` with body `{"id": 918273002, "name": "Rex", "status": "flying", "photoUrls": ["https://example.com/pet.jpg"]}`
3. `POST /pet` with body `{"id": 918273003, "name": "Rex", "status": "available"}` (no `photoUrls`)
4. `POST /pet` with body `{"id": 918273004, "status": "available"}` (no `name`, no `photoUrls`)
5. `POST /pet` with body `{"id": 918273005, "name": "Rex", "status": "Available", "photoUrls": ["https://example.com/pet.jpg"]}` (enum value in the wrong case)
6. `POST /pet` with body `{"id": 918273006, "name": "Rex", "status": "", "photoUrls": ["https://example.com/pet.jpg"]}` (empty status)
7. `POST /pet` with body `{"id": 918273007, "name": "", "photoUrls": ["https://example.com/pet.jpg"]}` (empty `name`)
8. `POST /pet` with body `{"id": 918273008, "name": "Rex", "photoUrls": []}` (empty `photoUrls`)
9. `POST /pet` with body `{"id": 918273009, "name": null, "photoUrls": ["https://example.com/pet.jpg"]}` (`name` is `null`)
10. `POST /pet` with body `{"id": 918273010, "name": "Rex", "photoUrls": null}` (`photoUrls` is `null`)
11. `POST /pet` with body `{"id": 918273011, "name": 123, "photoUrls": ["https://example.com/pet.jpg"]}` (`name` is a number)
12. `POST /pet` with body `{"id": 918273012.5, "name": "Rex", "photoUrls": ["https://example.com/pet.jpg"]}` (a decimal Id)
13. `POST /pet` with body `{"id": 918273013, "name": "Rex", "photoUrls": ["https://example.com/pet.jpg"], "tags": null}` (`tags` is `null`)
14. `GET /pet/{id}` for each Id from steps 1-13 (`918273012` for step 12)

## Expected

- Steps 1-13 are rejected with `405 Invalid input`.
- Step 14 returns `404` for all thirteen: nothing invalid is stored.

Basis: steps 1-6, the contract (`required`, `enum` and the `405` response of `POST /pet`). Steps 7-8, an
assumption, to be agreed with the API owners: a required field must hold a value, so an empty `name` or an empty
`photoUrls` list counts as missing (the spec sets no `minLength` or `minItems`). The spec gives `405` no schema,
so no response body or message is expected. Steps 9-10, the contract: `name` is a `string` and `photoUrls` an
`array`, and Swagger 2.0 has no `null` for either. Steps 11-13, the contract: `name` is a `string`, `id` an
`integer` and `tags` an `array` (no `null`). Step 14, an assumption: a rejected pet is not added
(the spec doesn't say so).

## Actual

- Step 1 returns `200` with `{"id":918273001,"photoUrls":["https://example.com/pet.jpg"],"tags":[],"status":"available"}`.
- Step 2 returns `200` with `{"id":918273002,"name":"Rex","photoUrls":["https://example.com/pet.jpg"],"tags":[],"status":"flying"}`.
- Step 3 returns `200` with `{"id":918273003,"name":"Rex","photoUrls":[],"tags":[],"status":"available"}`.
- Steps 4-6 return `200` too: `{"id":918273004,"photoUrls":[],"tags":[],"status":"available"}`, `"status":"Available"`
  and `"status":""` are stored as sent (2026-11-17).
- Steps 7-8 return `200`: `"name":""` and `"photoUrls":[]` are stored as sent (2026-11-17).
- Steps 9-10 return `200`. Step 9 stores a pet without `name`; step 10 stores a pet without `photoUrls`, and its
  `GET` returns `{"id":918273010,"name":"Rex","tags":[]}`: the reply itself breaks the spec, which requires
  `photoUrls` in every `Pet` (2026-11-17).
- Steps 11-13 return `200`: `"name":"123"` is stored, the decimal Id is stored as `918273012`, and `"tags": null`
  is stored without `tags` (2026-11-17). `"photoUrls": [1]` (stored as `["1"]`) and `"category": null` behave the same.
- All thirteen pets are stored (rechecked 2026-11-17).

## Notes

The linked scenarios check step 14 only after a `405`. A `GET` by the sent Id after an accepted or failed
`POST` proves nothing: the pet could be stored under another Id.

The server already answers malformed JSON with `400 bad input`, so `400` may be the better code; the test
follows the published spec (`405`) until the spec is changed.

## Impact

Data that breaks the contract gets into the store and reaches every client that reads it.
