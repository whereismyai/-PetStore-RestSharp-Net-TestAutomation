# BUG-006: GET /pet/{id} with an unsupported Accept header returns 500 instead of 406

- Id: BUG-006
- Status: Open
- Title: GET /pet/{id} with an unsupported Accept header returns 500 instead of 406
- Raised: 2026-11-16
- Endpoint: GET /pet/{petId}
- Environment: https://petstore.swagger.io/v2
- Linked test: `Getting a pet in a media type the API does not produce is rejected with 406 Not Acceptable` (`@bug:BUG-006`, PetStore_Pet_Http.feature)

## Description

`GET /pet/{petId}` produces only `application/json` and `application/xml` (`produces` in `swagger.json`).
A request whose `Accept` header asks for anything else, e.g. `text/plain` or `text/html`, fails with
`500 Server Error` and an HTML error page, instead of a client error.

## Steps to reproduce

1. `POST /pet` with body `{"id": 8800771234599, "name": "Pluto", "photoUrls": ["https://example.com/pet.jpg"]}` -> `200`
2. `GET /pet/8800771234599` with header `Accept: text/plain`
3. `GET /pet/8800771234599` with header `Accept: application/xml` (control)

## Expected (assumption, to be agreed with the API owners)

- Step 2 returns `406 Not Acceptable`.
- Step 3 returns `200` with `Content-Type: application/xml` (works today).

Basis: the contract lists the media types the operation produces, but defines no response for an `Accept` it
cannot satisfy. [RFC 9110, section 12.5.1](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.1) lets the
server either answer `406` or ignore the header and send one of its own types. `406` is assumed because it
tells the client what went wrong. If the owners prefer to ignore the header, close this bug with
`Resolution: Works as designed` and change the scenario to expect `200` with `Content-Type: application/json`.
A `5xx` is wrong either way: the request is valid HTTP, and nothing failed on the server's side.

## Actual

- Step 2 returns `500` with `Content-Type: text/html; charset=ISO-8859-1` and a Jetty error page (rechecked
  2026-11-16): `javax.ws.rs.WebApplicationException: com.sun.jersey.api.MessageException: A message body writer
  for Java class io.swagger.sample.model.ApiResponse ... and MIME media type application/octet-stream was not
  found`, followed by the full Java stack trace.
- The same `500` comes back for a pet that does not exist and for `Accept: text/html`.

## Impact

Clients get a server error for a client-side choice and cannot tell it from a real outage; monitoring counts
it as one.

Side note, not part of the expected result: the error page exposes the full stack trace and the server's
libraries (Jetty, Jersey, class names), which leaks implementation details.
