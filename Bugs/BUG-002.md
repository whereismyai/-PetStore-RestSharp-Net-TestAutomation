# BUG-002: POST /pet without an Id gives every pet the same generated Id

- Id: BUG-002
- Status: Open
- Title: POST /pet without an Id gives every pet the same generated Id
- Raised: 2026-11-14
- Endpoint: POST /pet
- Environment: https://petstore.swagger.io/v2
- Linked test: `Pets created without an Id or with Id 0 get their own generated Ids` (`@bug:BUG-002`, PetStore_Pet_E2E.feature)

## Description

Data loss. On some runs, every pet created without an Id (field missing or `null`) gets the same Id,
`9223372036854775807` (the int64 maximum), so each such pet replaces the previous one. Only the last pet
created without an Id still exists.

## Steps to reproduce

1. `POST /pet` with body `{"name": "Toothless", "category": {"name": "DRAGONS"}, "photoUrls": ["https://example.com/pet.jpg"]}`
2. `POST /pet` with body `{"id": null, "name": "Toothless", "category": {"name": "NIGHT_FURY"}, "photoUrls": ["https://example.com/pet.jpg"]}`
3. `GET /pet/9223372036854775807`

## Expected

- Steps 1 and 2 return two different Ids.
- Each pet can be read back by its own Id with its own category.

Basis: an Id identifies exactly one pet (`GET` and `DELETE` address a pet by it). The spec does not say how the
server assigns an Id when none is sent; it only defines `id` as an int64.

## Actual

- Steps 1 and 2 both return `"id": 9223372036854775807`.
- Step 3 returns the second pet (`NIGHT_FURY`); the first pet is gone.

## Reproduction conditions

Intermittent. Reproduced on 2026-11-13, 2026-11-14 and 2026-11-16. Did not reproduce on 2026-11-15: steps 1
and 2 returned different Ids (`9223372036854022629`, `9223372036854022630`). The bug was closed as Cannot
reproduce that day and reopened on 2026-11-16, when both pets got `9223372036854775807` again.

No condition that reliably triggers it is known from the outside. It reproduces whenever every generated Id
comes back as the int64 maximum.

## Observations

Facts seen on the public server, not explained by the spec:

- A generated Id is one more than the highest existing Id. An Id freed by `DELETE` goes to the next pet
  (`9223372016900018801` was deleted, and the next pet got it).
- Generated Ids are already close to the maximum: `9223372036854022631` is 753 176 below it.

## Hypotheses (not confirmed)

The server is a black box and is shared with other users, so neither can be confirmed from the outside:

- **Overflow at the int64 maximum.** Fits the observations: while any user's pet sits at the int64 maximum,
  every generated Id ends up at it; once that pet is deleted, Ids are distinct again. That would explain
  why the bug comes and goes.
- **A race condition in Id generation.** Concurrent `POST` requests could read the same highest Id. Not
  tested: confirming it needs server-side access or a controlled load test.

## Impact

Clients that rely on server-generated Ids silently overwrite each other's data. Deleting "your" pet
deletes whatever pet currently holds that Id.
