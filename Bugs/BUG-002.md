# BUG-002: POST /pet without an Id gives every pet the same generated Id

- Id: BUG-002
- Status: Open
- Title: POST /pet without an Id gives every pet the same generated Id
- Raised: 2026-11-14
- Endpoint: POST /pet
- Environment: https://petstore.swagger.io/v2
- Linked test: `Pets created without an Id or with Id 0 get their own generated Ids` (`@bug:BUG-002 @intermittent`, PetStore_Pet.feature)

## Description

On some runs, every pet created without an Id (field missing or `null`) gets the Id `9223372036854775807` (the
largest int64). While that happens, each such pet replaces the previous one: only the last pet created without an Id exists.

## Steps to reproduce

1. `POST /pet` with body `{"name": "Toothless", "category": {"name": "DRAGONS"}, "photoUrls": ["https://example.com/pet.jpg"]}`
2. `POST /pet` with body `{"id": null, "name": "Toothless", "category": {"name": "NIGHT_FURY"}, "photoUrls": ["https://example.com/pet.jpg"]}`
3. `GET /pet/9223372036854775807`

## Expected

- Steps 1 and 2 return two different generated Ids.
- Each pet can be read back by its own Id with its own category.

## Actual

- Steps 1 and 2 both return `"id": 9223372036854775807`.
- Step 3 returns the second pet (`NIGHT_FURY`); the first pet is gone.

Reproduced on 2026-11-13, 2026-11-14 and 2026-11-16; did not reproduce on 2026-11-15. The bug is intermittent.

## Retests

- 2026-11-15: did not reproduce. Steps 1 and 2 returned different Ids (`9223372036854022629`, `9223372036854022630`).
  Closed as Cannot reproduce, because nothing showed that the server was fixed.
- 2026-11-16: reproduced again. Both pets got `9223372036854775807`. Reopened as intermittent: the linked test
  is tagged `@intermittent`, so it keeps running while the bug is Open and each failure adds evidence.

## Possible cause

The server is a black box to us and is shared with other users, so the cause cannot be confirmed from the outside.
Two hypotheses:

- **Overflow at the int64 maximum (supported by observations).** A generated Id looks like the highest existing
  Id + 1: an Id freed by `DELETE` goes to the next pet (`9223372016900018801` was deleted, and the next pet got
  it), and generated Ids are already close to the maximum (`9223372036854022631`, 753 176 below it). While any
  user's pet sits at the int64 maximum, every generated Id overflows to it; once that pet is deleted, Ids are
  distinct again. That would explain why the bug comes and goes.
- **A race condition in Id generation (not tested).** Concurrent `POST` requests could read the same highest Id.
  Confirming it needs server-side access or a controlled load test, which this project does not have.

## Impact

Clients that rely on server-generated Ids silently overwrite each other's data. Deleting "your" pet
deletes whatever pet currently holds that Id.
