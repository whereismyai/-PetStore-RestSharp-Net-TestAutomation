# BUG-004: GET and DELETE /pet/{id} with an invalid Id return 404 instead of 400

- Id: BUG-004
- Status: Open
- Title: GET and DELETE /pet/{id} with an invalid Id return 404 instead of 400
- Raised: 2026-11-14
- Updated: 2026-11-15 (DELETE and Ids beyond int64 added)
- Endpoints: GET /pet/{petId}, DELETE /pet/{petId}
- Environment: https://petstore.swagger.io/v2
- Linked test: `Getting or deleting a pet by an invalid Id is rejected with 400` (`@bug:BUG-004`, PetStore_Pet_Validation.feature)

## Description

The spec defines `400 Invalid ID supplied` for `GET /pet/{petId}` and `DELETE /pet/{petId}`. An Id that is not
an int64 (non-numeric, or beyond the int64 maximum) is answered with `404` instead.

## Steps to reproduce

1. `GET /pet/abc`
2. `GET /pet/9223372036854775808` (int64 maximum + 1)
3. `DELETE /pet/abc`
4. `DELETE /pet/9223372036854775808`

## Expected

- `400` for each request.

Basis: the contract defines `400` for an invalid Id. Its description, `Invalid ID supplied`, is not a
required message: the response has no schema, so the tests check the status code only.

## Actual

- Each request returns `404` with `{"code":404,"type":"unknown","message":"java.lang.NumberFormatException: For input string: \"<id>\""}`,
  e.g. `For input string: \"abc\"`.

## Impact

Clients cannot tell a malformed request from a missing pet.

Side note, not part of the expected result: the message exposes the server's internal exception
(`java.lang.NumberFormatException`), which leaks implementation details.
