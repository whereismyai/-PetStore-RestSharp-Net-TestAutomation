# BUG-001: POST /pet with an existing Id silently overwrites the existing pet

- Id: BUG-001
- Status: Open
- Title: POST /pet with an existing Id silently overwrites the existing pet
- Raised: 2026-11-14
- Endpoint: POST /pet
- Environment: https://petstore.swagger.io/v2
- Linked tests: `Creating a pet with an existing ID is rejected with 409 Conflict` and `Creating a pet with an existing ID keeps the existing pet` (`@bug:BUG-001`, PetStore_Pet.feature)

## Description

Creating a pet with an Id that already belongs to another pet is not rejected. The API answers `200`
and replaces the existing pet with the new data (upsert), so the original pet is lost without any error.

## Steps to reproduce

1. `POST /pet` with body `{"id": 770001, "name": "First", "status": "available", "photoUrls": [], "tags": []}` -> `200`
2. `POST /pet` with body `{"id": 770001, "name": "Second", "status": "sold", "photoUrls": [], "tags": []}`
3. `GET /pet/770001`

## Expected

- Step 2 is rejected with `409 Conflict` (an Id that already exists cannot be created again).
- Step 3 returns the original pet: `name = First`, `status = available`.

The spec defines no response for a duplicate Id on `POST /pet` (only `405 Invalid input`); `409 Conflict`
is the HTTP-standard answer and is an assumption to confirm with the API owners. The part that does not
depend on the code is step 3: creating must never replace an existing pet (`PUT /pet` exists for updates).

## Actual

- Step 2 returns `200` with `{"id":770001,"name":"Second","photoUrls":[],"tags":[],"status":"sold"}`.
- Step 3 returns `200` with the overwritten pet: `name = Second`, `status = sold`.

## Impact

Any client that creates pets with explicit Ids can destroy existing data without noticing.
While this bug is `Open`, the linked scenario is skipped by the `BugHooks` before-scenario hook.
Set `Status: Fixed` (or `Closed`) once the API is fixed - the scenario runs again automatically.
